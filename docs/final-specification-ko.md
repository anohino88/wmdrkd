# AUGMENTWILD · 최종 통합 개발 프롬프트

## 0. 최상위 목표

너는 Minecraft Paper 플러그인 개발자, 서버 아키텍트, 게임 시스템 설계자, 테스트 엔지니어다.

기존 GitHub 프로젝트 **AugmentWild / 증강 야생**을 실제 Minecraft 서버에서 여러 플레이어가 정상적으로 즐길 수 있는 완성된 FFA 미니게임으로 개발하라.

단순히 클래스와 메서드를 생성하거나 테스트 수치를 늘리는 것이 목표가 아니다.

최종 목표는 다음과 같다.

- 실제 Paper 서버에 설치 가능한 JAR
- 정상적인 경기 시작과 종료
- 기존 월드 기반 랜덤 경기장
- 파밍 중에도 가능한 PvP
- 매번 다른 안전한 랜덤 리스폰
- 증강 64종과 진화·시너지
- 보급 및 플레이어 탐지
- 자기장 축소와 최종 승리 판정
- 전체 관리자 설정
- 지속적인 게임 안정성
- 8~16명 규모의 실제 플레이 검증

**직업 시스템은 구현하지 않는다.**

작업은 기존 코드를 분석하고 최대한 재사용하는 방식으로 진행한다.

기존에 관련 코드가 있다면 다른 시스템에 영향을 주지 않는 범위에서 비활성화하거나 정리한다.

# 3. 게임 기본 구조

게임 모드:

**FFA 개인전**

기본 참가 인원:

- 최소 2명
- 최대 16명
- 권장 8명

향후 팀전 지원을 위한 확장 가능성은 유지하되, 첫 출시에서는 FFA를 완성한다.

전체 흐름:

```text
WAITING
   ↓
PREPARING
   ↓
랜덤 경기장 선정
   ↓
플레이어 안전 배치
   ↓
GATHERING
   ↓
30분 파밍 + 자유 PvP
   ↓
5분마다 증강 선택
   ↓
30분 최종 프리즘 선택
   ↓
30분 20초
   ↓
목숨 제한 적용 + 자기장 축소
   ↓
최종 60×60 안전 구역
   ↓
SUDDEN_DEATH
   ↓
마지막 생존자 결정
   ↓
ENDING
   ↓
CLEANUP
```

Paper 이벤트에서 직접 임의로 경기 상태를 변경하는 구조를 만들지 마라.

# 4. 경기 시간표

모든 시간은 중앙 `MatchClock`을 기준으로 한다.

| 경기 시간 | 이벤트 |
|---|---|
| 00:00 | 경기 시작, 무작위 안전 스폰, 파밍 및 PvP 허용 |
| 05:00 | 증강 선택 1 |
| 10:00 | 증강 선택 2 |
| 13:00 | 일반 보급 예고 |
| 14:00 | 일반 보급 위치 공개 |
| 15:00 | 증강 선택 3, 일반 보급 2개 등장 |
| 20:00 | 증강 선택 4 |
| 23:00 | 고급 보급 예고 |
| 24:00 | 고급 보급 위치 공개 |
| 25:00 | 증강 선택 5, 고급 보급 2개 등장 |
| 30:00 | 증강 선택 6, 프리즘 3개 중 하나 확정 |
| 30:20 | 목숨 제한 단계 시작, 자기장 축소 시작 |
| 40:20 | 자기장 60×60 도달, 서든데스 |
| 이후 | 최종 승자 결정 |

## 중요: 파밍 중 PvP 허용

이전 명세의 `gathering.pvp-enabled: false`는 사용자의 최신 결정과 충돌한다.

이를 `true`로 변경한다.

30분 20초는 더 이상 PvP 최초 허용 시점이 아니다.

이 시점부터 달라지는 것은 다음과 같다.

- 사망 시 목숨 차감
- 탈락 가능
- 자기장 축소
- 게임 후반부 규칙 적용

기존 `PVP`라는 내부 상태명은 유지해도 된다.

다만 UI와 안내 메시지에는 `PvP 시작` 대신 `목숨 제한 시작`, `자기장 축소 시작`처럼 실제 동작을 정확히 표현한다.

# 5. 게임 시간과 일시정지

경기 시계는 다음을 구분한다.

- 실제 경과 시간
- 경기 경과 시간
- 현재 단계 경과 시간
- 증강 선택으로 정지된 시간
- 관리자 수동 일시정지 시간

기본 규칙:

`pause-match-clock-during-selection: true`

따라서 증강 선택 중에는 다음 요소의 경기 시간이 정지한다.

- 다음 증강 선택
- 보급 등장
- 목숨 제한 단계 시작
- 자기장 축소
- 서든데스 진입
- 경기 시간에 종속된 리스폰 대기

단, 증강 선택 GUI의 15초 입력 제한은 실제 시간 기준으로 동작한다.

## 동일 시각 이벤트

무작위 보급이 증강 선택과 같은 경기 시각에 예정되면 선택을 먼저 처리한다.

순서:

1. 해당 경기 시각 도달
2. 증강 선택 시작
3. 경기 시계 정지
4. 선택 종료 또는 제한시간 만료
5. 경기 시계 재개
6. 같은 시각의 보급 등장 처리

이벤트 누락이나 중복 실행을 방지한다.

TPS 저하가 있어도 동일 이벤트를 두 번 실행하지 않는다.

# 6. 기존 월드 랜덤 경기장

매 경기 기존 월드에서 새로운 경기장 영역을 선정한다.

기본 크기:

**1000×1000 블록**

금지:

- 매 경기 월드 생성
- 기존 월드 삭제
- 월드 복제
- 블록 롤백
- 월드 시드 변경
- 강제 WorldEdit 의존
- 비참가자의 월드 보더 변경

## 경기장 검색

`ArenaSearchService`를 구현하거나 기존 해당 기능을 완성한다.

탐색 과정:

1. 기존 지정 월드 확인
2. 검색 반경 내 후보 중심점 추첨
3. 1000×1000 영역 산출
4. 월드 경계 검증
5. 과거 사용 경기장과 겹침 검사
6. 중심·모서리·가장자리의 거친 바이옴 검사
7. 내부 정밀 바이옴 검사
8. 지표면 기준 바다 바이옴 검증
9. 안전한 플레이어 스폰 가능 여부 확인
10. 최종 경기장 확정

기본 정책:

`ocean-policy: ZERO`

검증 해상도에서 바다 바이옴이 하나라도 발견되면 후보를 거부한다.

실제로 검사하지 않은 영역까지 무조건 바다가 없다고 주장하지 않는다.

## 사용 기록

`used-regions.yml`에 기록한다.

- match ID
- world ID
- 중심 좌표
- 경기장 크기
- 시작·종료 시간
- 검사 정책

기존 경기장과 AABB가 겹치거나 설정된 완충 거리 이내인 후보를 거부한다.

## 검색 실패

120초 및 설정된 최대 시도 횟수 안에 경기장을 찾지 못했다면:

- 실제 경기 시작 취소
- 참가자 안전 복귀
- 검색 작업 정리
- 관리자에게 실패 원인 표시

검증 실패를 숨기고 바다나 위험 지역을 선택하지 마라.

# 7. 경기 시작 스폰

경기가 정상적으로 준비되면 모든 참가자를 경기장 내부의 서로 다른 랜덤 안전 위치에 배치한다.

기본 플레이어 간 최소 거리:

**80블록**

안전 조건:

- 경기장 내부
- 바다 바이옴 제외
- 물 및 용암 제외
- 질식 위험 없음
- 머리 공간 확보
- 바닥 안전
- 동굴 내부 제외
- 높은 낙하 위험 제외
- 위험 블록 주변 제외
- 경기장 가장자리와 충분한 거리

최소 거리 확보가 어려운 경우 거리를 단계적으로 완화할 수 있지만, 지형 안전성은 완화하지 않는다.

플레이어를 경기 시작 전에 이동시키기 위한 스냅샷 저장에 실패하면 해당 플레이어를 안전하게 처리하고 경기 시작을 중단한다.

# 8. 파밍 중 PvP와 무한 부활

파밍 단계는 기본 30분이다.

이 단계에서는 다음이 가능하다.

- 광물 채굴
- 몬스터 사냥
- 장비 제작
- 탐험
- 다른 플레이어 공격
- 다른 플레이어 처치
- 보급 획득
- 증강 효과 사용

**파밍 중 PvP 공격을 취소하지 마라.**

하지만 파밍 중 사망으로 PvP 단계의 목숨을 소모하지 않는다.

파밍 중 100번 사망하더라도 탈락하지 않는다.

사망 시:

- 인벤토리 유지
- 갑옷 유지
- 보조 손 유지
- 경험치 유지
- 증강 유지
- 영구 중첩 유지
- 진화 진행도 유지
- 아이템 드롭 방지
- 경험치 드롭 방지
- 20초 리스폰 대기

중복 사망 이벤트 때문에 같은 플레이어가 두 번 사망 처리되어서는 안 된다.

# 9. 매번 랜덤 리스폰

이번 프로젝트의 필수 요구사항이다.

**플레이어가 죽을 때마다 경기장 내부에서 새로운 안전 좌표를 무작위로 선정한다.**

고정 리스폰 지점을 정상 게임 규칙으로 사용하지 않는다.

## 리스폰 위치 검사

후보 위치는 다음 조건을 만족해야 한다.

1. 현재 경기장에 속한 월드
2. 경기장 직사각형 내부
3. 현재 자기장 안전 구역 내부
4. 안전한 지표면
5. 발과 머리가 들어갈 공간
6. 물속 또는 용암 속이 아님
7. 위험 블록 위가 아님
8. 충분한 경계 여유
9. 다른 생존 플레이어와 가능한 한 거리 확보
10. 플레이어의 직전 리스폰 위치와 가능한 한 다름

한 번 추첨한 후보를 검증 없이 사용하지 않는다.

## 자기장 축소 시

현재 자기장이 300×300으로 축소됐다면 그 내부에서만 좌표를 선정한다.

최종 60×60에서는 60×60 내부에서만 좌표를 선정한다.

거리 조건을 충족할 수 없는 상황에서는 최소 거리만 완화한다.

자기장 밖으로 내보내는 방식의 대체 처리는 금지한다.

## 청크 및 서버 성능

- 탐색 횟수 제한
- 동시 청크 요청 제한
- 메인 스레드 작업량 제한
- Paper API 스레드 안전성 준수
- 안전 위치 캐시 활용 가능
- 실제 텔레포트 직전 재검증

무제한 청크 로딩이나 전역 블록 스캔으로 TPS를 떨어뜨리지 않는다.

## 좌표 탐색 실패

유효한 위치를 찾지 못하면:

- 해당 플레이어를 계속 안전 대기 상태로 유지
- 부활 예약 유지
- 다른 위치 재탐색
- 실패 원인 로그 기록
- 최대 재시도 정책 적용

월드 기본 스폰이나 경기장 밖 좌표로 보내지 않는다.

# 10. 사망·리스폰 상태 일관성

기존 `GameSession`의 `LifeState` 및 `RespawnReservation`을 재사용한다.

다음 문제를 해결한다.

- 동일 사망 이벤트 중복
- 이벤트 발생 당시와 처리 시점의 경기 단계 불일치
- PvP 전환과 사망 동시 발생
- 서든데스 전환과 사망 동시 발생
- 예약 만료와 탈퇴 충돌
- 서버 기본 리스폰과 경기 리스폰 불일치
- 실패한 텔레포트 이후 ACTIVE 전환
- 다른 경기의 오래된 예약 실행

## 사망 시점 보존

사망 의도를 UUID만으로 기록하지 않는다.

경기 ID, 플레이어 ID, 사망 순번, 사건 발생 당시 경기 시각과 단계에 해당하는 정보를 보유한다.

사망 판정에는 원래 사건의 단계 규칙을 사용한다.

여러 플레이어가 같은 논리 틱에 사망했다면 전부 반영한 뒤 승리 여부를 평가한다.

## 안전한 리스폰 순서

1. 사망 이벤트 기록
2. 중복 사망 검증
3. 목숨 및 부활 증강 판정
4. 리스폰 예약 생성
5. 기본 네이티브 리스폰 처리
6. 20초 대기
7. 랜덤 안전 좌표 탐색
8. 청크 준비
9. 좌표 재검증
10. 플레이어 이동
11. 이동 성공 확인
12. 리스폰 예약 확정 소비
13. ACTIVE 전환
14. 부활 보호 적용

실제 이동이 실패했는데 도메인에서 ACTIVE로 변경되지 않도록 한다.

## 리스폰 중 행동 제한

- 공격 금지
- 피해 유발 금지
- 블록 설치·파괴 금지
- 아이템 사용 금지
- 인벤토리 조작 제한
- 보급 획득 금지
- 플레이어 탐지 금지
- 증강 발동 금지

관전자 모드를 사용한다면 상대 위치를 무제한 정찰하는 악용을 방지한다.

기존 `PaperRespawnRestrictions`가 자체 복귀 텔레포트까지 취소하지 않도록 검증된 내부 이동을 별도로 허용한다.

## 부활 보호

기본 3초.

- 모든 외부 피해 보호
- 보호 중 공격도 불가능
- 보호 시간 종료 후 정상 전투
- 중복 타이머 생성 금지
- 경기 종료 시 즉시 해제

# 11. PvP 목숨 제한 단계

30분 20초가 되면 목숨 제한 규칙이 적용된다.

기본 목숨:

**2개**

- 첫 일반 사망: 남은 목숨 1, 20초 대기 후 랜덤 부활
- 두 번째 일반 사망: 남은 목숨 0, 최종 탈락

파밍 중 사망 횟수는 목숨에 영향을 주지 않는다.

증강으로 사망이 방지됐을 경우 일반 목숨을 차감하지 않는다.

사망 처리 우선순위:

1. 사망 방지 증강
2. 즉시 부활 증강
3. 일반 사망 처리
4. 단계별 목숨 규칙
5. 최종 탈락 판단
6. 승리 판정 요청

한 번의 치명타 사건에 여러 부활 증강을 중복 소비하지 않는다.

# 12. 서든데스

자기장이 최종 60×60에 도달하면 서든데스로 전환한다.

기본 규칙:

- 사망 시 최종 탈락

- 설정된 부활 증강의 우선순위 적용
- 마지막 생존자가 승리

`allow-existing-respawn: true`

승리 후보에 포함할 플레이어와 이미 탈락한 플레이어를 구분한다.

승리 판정은 개별 Bukkit 이벤트마다 실행하지 않고 논리 틱 단위로 확정한다.

# 14. 플레이어 탐지 기능

일반 명령어:

`/aw locate`

별칭:

`/aw track`

기본 비용:

**다이아몬드 1개**

기본 쿨타임:

60초

대상 선정 조건:

- 같은 경기
- 자신 제외
- ACTIVE
- 접속 중
- 같은 월드
- 최종 탈락하지 않음
- 리스폰 대기 중이지 않음

대상은 3차원 유클리드 거리 기준 가장 가까운 플레이어다.

표시는 8방향으로 제한된다. 이름은 설정에 따라 공개할 수 있으며 기본값은 비공개다.
좌표, 높이 및 거리는 표시하지 않는다. 경기 시간 10초 동안 방향을 갱신하며 대상이 현재 안전 구역을 벗어나거나 추적 불가능해지면 종료한다.

## 아이템 차감 원칙

- 대상 없음: 차감 없음
- 다이아몬드 부족: 차감 없음
- 명령 실패: 차감 없음
- 성공: 정확히 1개 차감

비용 차감과 성공 결과를 단일 서버 메인 스레드 작업에서 일관되게 처리한다.

동일 요청이 중복 처리되어도 다이아몬드를 두 번 소비하지 않는다.

기존 `Tracker`의 3차원 거리와 UUID 동률 규칙을 사용한다.

# 17. 증강 64종 구현

증강의 정확한 ID, 한국어 이름, 수치, 발동 조건, 쿨타임, 중첩, 예외 규칙은 저장소의 `docs/specification-ko.md`를 최우선으로 사용한다.

기존 문서에 정의된 **최신 핵심 30종과 추가 34종, 총 64종**을 구현 대상으로 한다.

구형 증강 후보는 기본 선택 풀에 포함하지 않는다.

## 구현 순서

### 1차: 증강 엔진

- 증강 등록
- 증강 선택
- 등급 추첨
- 효과 발동
- 쿨타임
- 중첩
- 상태 유지
- 상태 제거
- 피해 파이프라인
- 부활 효과
- 연쇄 효과 제한

### 2차: 핵심 30종

- SILVER 8종
- GOLD 10종
- PRISMATIC 12종

문서에 정의된 수치를 정확히 적용한다.

### 3차: 진화·시너지

진화 시스템과 시너지 엔진을 구현한다.

### 4차: 추가 34종

핵심 증강 안정화 이후 추가한다.

최종적으로 64종 모두 실제 효과가 동작해야 한다.

## 미구현 정책

미완성 증강은 다음처럼 관리한다.

`implemented: false`

선택 풀에서 제외한다.

관리자 목록에서는 미완성 상태를 표시한다.

실제로 작동하지 않는 효과를 `implemented: true`로 표시하지 마라.

# 18. 증강 엔진 안정성

다음 기능을 공통 엔진으로 구현한다.

- DamagePipeline
- ValidHitPolicy
- AugmentProcDispatcher
- AugmentCooldownManager
- AugmentStackManager
- AugmentEvolutionManager
- AugmentSynergyManager
- ReviveResolver
- NaturalOreTracker
- EligibleMobPolicy
- MovementProgressTracker

기존 동등한 기능이 있다면 재사용한다.

## 무한 연쇄 방지

기본 최대 연쇄 깊이:

`max-proc-depth: 2`

각 공격 연쇄에 고유 ID를 부여한다.

한 증강으로 발생한 추가 피해가 무한히 같은 증강을 발동시키지 못하게 한다.

예:

- 마법 미사일이 자기 자신을 무한 생성하지 않음
- 무한 반복이 자기 자신을 재발동하지 않음
- 히드라 추가 공격이 무한 증식하지 않음

## 중첩

일부 증강의 최대 중첩은 디자인상 무제한이다.

단, 서버 수치 안정성을 위한 별도 상한을 둔다.

- 정수 오버플로 방지
- NaN/Infinity 거부
- 최대 체력 안전 상한
- 피해 배율 안전 상한
- 이동속도 안전 상한
- 과도한 연쇄 효과 방지

디자인상 무제한 중첩과 서버 엔진의 안전 제한을 구분한다.

## 악용 방지

- 플레이어가 설치한 광석 재채굴 악용 차단
- 갑옷 거치대 및 테스트 몹 반복 타격 악용 차단
- 동일 몹의 처치 중첩 지급 방지
- 텔레포트를 이동 거리 중첩으로 계산하지 않음
- 자기 자신에게 가한 피해로 공격 중첩을 얻지 않음

# 19. 증강 진화와 시너지

기존 명세의 진화 6개와 시너지 5개를 모두 구현한다.

## 진화

대상:

- steel_heart
- magic_missile
- sword_wind
- infernal_conductor
- tank_engine
- berserk_engine

진화 조건과 강화 수치는 기존 명세를 따른다.

진화는 중복 적용되지 않아야 한다.

## 시너지

기본 시너지:

1. 강철의 왕
2. 무한 포격
3. 재앙의 기관차
4. 지옥의 군주
5. 천 개의 검

요구 증강을 모두 보유했을 때만 발동한다.

시너지 획득 시 공지와 효과를 표시한다.

시너지 계산을 매 틱 전체 증강 목록 탐색으로 처리하지 않고 증강 획득·제거 이벤트 중심으로 처리한다.

모든 수치는 `synergies.yml` 및 관련 설정으로 관리한다.

# 27. 기존 코드에서 확인된 결함 수정

다음 항목은 특별히 우선 점검한다.

## A. 사망 단계 경계

현재 `PaperMatchService.tick()`에서 시간표 갱신 후 사망을 처리하는 구조가 사망 당시의 경기 단계와 처리 당시 단계를 다르게 만들 수 있다.

이 문제를 수정한다.

## B. 네이티브 리스폰 완료

`PlayerRespawnEvent`만으로 서버 측 상태 복원이 완전히 완료됐다고 가정하지 않는다.

실제 Paper 버전의 적절한 후속 리스폰 이벤트 및 호출 시점을 검증한다.

## C. 텔레포트 차단

리스폰 대기자의 임의 이동은 막되, 플러그인이 수행하는 검증된 복귀 이동까지 취소하지 않는다.

## D. 예약 확정

안전한 위치를 찾지 못하거나 텔레포트에 실패했는데 ACTIVE가 되지 않도록 한다.

## E. 사망 아이템 복제

아이템 보존과 드롭 차단을 모두 처리한다.

다른 플러그인과의 이벤트 충돌도 테스트한다.

## F. 경기 종료

`clearMatch()` 호출 전에 승리 결과 및 복원 작업이 누락되지 않도록 한다.

## G. UI 문구

파밍 중 PvP가 가능한 규칙에 맞춰 기존 `PvP까지` 문구를 수정한다.

## H. 설정 불일치

직업 제외, 파밍 PvP 허용, 랜덤 리스폰 정책을 실제 설정과 문서에 반영한다.

같은 문제의 검사 보고서만 반복해서 커밋하지 마라.

- 직업 시스템 추가
- 시작 직업 선택 UI 추가
- 파밍 중 PvP 차단

- 고정 리스폰 위치 사용

- 자기장 밖 리스폰

- 텔레포트 실패 후 ACTIVE 전환

- 증강 무한 연쇄

- 테스트 없이 완료 선언
- 컴파일되지 않은 코드를 정상 기능으로 보고
- 테스트 수치만 늘리고 실사용 기능을 방치
- 불필요한 신규 브랜치 생성
- 기존 프로젝트 전체 재작성

## 최종 작업 지시

지금부터 저장소의 실제 상태를 분석한 뒤, 가장 우선순위가 높은 미완성 기능부터 구현하라.

기존 명세와 충돌하는 규칙은 이 프롬프트의 최신 규칙으로 수정한다.

작업은 코드 구현, 테스트, 오류 수정, 빌드, 커밋까지 이어져야 한다.

네트워크 문제가 발생하면 가능한 다른 검증 경로를 이용하고, 차단된 항목과 구현 가능한 항목을 구분한다.

단순 작업 계획만 작성하고 종료하지 마라.

**AugmentWild를 직업이 없는 증강 중심 FFA 게임으로 완성하라. 파밍 중 PvP를 허용하고, 사망하면 경기장 내부의 매번 다른 안전한 위치에서 부활하도록 구현하라. 기존 월드와 플레이어 데이터를 보호하면서 모든 게임 시스템이 실제 Paper 서버에서 정상 동작하도록 개발하라.**
